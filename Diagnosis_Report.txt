  🤖 Issue 1 — Telegram Bot (Language Chaos + Broken Conversation Flow)
  
  3 root causes, all distinct:

  Language fragmentation

  Bot strings are split across 5 files with no single source of truth:

  ┌──────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │           File           │                                    Language                                     │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ BotMessages.java         │ All English                                                                     │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ BotUpdateDispatcher.java │ All Spanish ("Hola! Soy el bot de EQ51.", cancel prompts)                       │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ AgentOrchestrator.java   │ All Spanish (all business-logic responses hardcoded)                            │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ LlmIntentParser.java     │ English (system prompts tell the LLM to respond in English)                     │
  ├──────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ TareaBotActions.java     │ Mixed (English via BotMessages, Spanish fragments at sprint modification steps) │
  └──────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘

  The worst part: the LLM is instructed to respond in English, but AgentOrchestrator intercepts recognized intents and returns hardcoded Spanish strings. So
  structured commands → Spanish, free-form chat → English. Backwards.

  Conversation history is built but never used

  BotConversationManager correctly accumulates per-chat history in historialLlmPorChat. But BotUpdateDispatcher always calls orquestador.manejarMensaje(String) —
   the zero-history overload. The stored history is never retrieved and never passed to the LLM. Every single message is processed as if it's the first message
  of the conversation.

  Natural language can't start wizard flows

  The bot only launches multi-step workflows when it receives exact slash commands (/newtask, /assignsprint, etc.). AgentOrchestrator can correctly classify free
   text — "add task to sprint 4" → intent ASIGNAR_TAREA — but it has no bridge to actually start the wizard. It just returns a static redirect string. The next
  message (the task name) arrives with no wizard state and no history → bot treats it as a brand new isolated message → responds with "What would you like to do
  with [task name]?" That's exactly the symptom you described.

  🗄️  Issue 2 — Database User / Data Visibility

  The users explained

  ┌──────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
  │   Name   │                                                              What it actually is                                                               │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ EQUIPO51 │ The real Oracle ADB database user. The app connects as this user. All JPA tables (TAREAS, USUARIOS, etc.) live in the EQUIPO51 schema.         │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ admin    │ A Spring Security in-memory username. Completely unrelated to Oracle. Currently irrelevant — WebSecurityConfiguration.java sets                │
  │          │ anyRequest().permitAll() and disables all auth.                                                                                                │
  ├──────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
  │ ADMIN    │ Oracle ADB's built-in superuser. Shows up as the placeholder in .env.example. This is the source of confusion.                                 │
  └──────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

  No @Table(schema=...) annotations exist on any entity. No hibernate.default_schema is set. So Hibernate resolves all table references to the JDBC user's
  default schema — EQUIPO51.

  Why your SQL script data doesn't appear

  Schema mismatch. OCI Database Actions web console defaults to connecting as ADMIN. When you ran INSERT INTO TAREAS ... there, rows went into ADMIN.TAREAS. The
  app reads EQUIPO51.TAREAS. Two completely separate tables, neither sees the other's rows.

  To verify: In the OCI SQL console, run SELECT USER FROM DUAL; before your script. If it returns ADMIN, that's the problem.

  Fix: Either log into the OCI console as EQUIPO51 before running the script, or prefix every table: INSERT INTO EQUIPO51.TAREAS ...

  ⚙️  Issue 3 — GitHub Actions Failures

  Maven Build — 4 root causes

  1. Wrong Java version. build.yml sets java-version: '11'. Your pom.xml declares <java.version>17</java.version>. Spring Boot 3.x requires Java 17 minimum. JDK
  11 cannot compile this code. This alone causes a build failure before tests even run.
  2. Missing required env vars — no fallbacks. The workflow sets zero environment variables. application.properties has ${SPRING_ADMIN_PASSWORD} and
  ${TELEGRAM_BOT_TOKEN} with no default values. OracleConfiguration.java also injects ${ORACLE_DB_USERNAME} and ${ORACLE_DB_PASSWORD} with no defaults. Spring
  context fails at startup with IllegalArgumentException: Could not resolve placeholder — nothing runs.
  3. TelegramE2ETest requires a live Oracle ADB connection. It's annotated @SpringBootTest @ActiveProfiles("test"), but application-test.properties explicitly
  says spring.jpa.hibernate.ddl-auto=validate — it still tries to connect to Oracle ADB. CI has no wallet files. This test will always fail in GitHub Actions.
  4. OracleConfiguration activates on all non-dev profiles (@Profile("!dev")), including CI. The Oracle wallet doesn't exist in the runner — connection fails.

  Super Linter — 3 root causes

  1. Two duplicate Super Linter workflows exist. Both lint.yml and superlinter.yml trigger on push to main, using different versions (v7 vs v6) with conflicting
  configs. Double the failure emails, double the noise.
  2. superlinter.yml references a nonexistent file. It sets JAVA_FILE_NAME: google_checks.xml — that file doesn't exist in the repo. Only java_checks.xml exists.
   Checkstyle fails immediately trying to load a config that isn't there.
  3. Widespread AvoidStarImport violations. java_checks.xml has <module name="AvoidStarImport"/>. At least 10+ files use wildcard imports (import
  org.springframework.web.bind.annotation.*;, import jakarta.persistence.*;, import static org.mockito.Mockito.*;, etc.). When Checkstyle runs with the correct
  config, it fails on all of them.
